# Custom-agent formats across coding harnesses

Research date: 2026-10-29. Scope: reusable custom agents/subagents, **not** skills or generic `AGENTS.md` instructions. Evidence below is current first-party documentation/source; no harness was executed. Documentation and default behavior change, so installation support needs a tested version range rather than an undated compatibility badge.

## Capability matrix

## Compatibility details that affect an installer

- **There is no universal Markdown-agent format established by these sources.** A reusable common subset is agent name, a delegation description, and Markdown instructions; even the instruction slot is a system prompt in some harnesses and `developer_instructions` in Codex. Treat this as an agnthub product contract, not an existing cross-harness standard. [Claude](https://code.claude.com/docs/en/sub-agents#write-subagent-files), [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents), [Gemini](https://geminicli.com/docs/core/subagents/#file-format)
- **Names and collisions differ.** Claude/Codex/omp use a declared name; OpenCode uses the filename; Copilot CLI uses a file/subdirectory-derived ID and can load equal display names. Copilot CLI gives a personal definition priority over a repository definition of the same ID, whereas Cursor and omp document project-first behavior. A registry's stable agent ID cannot safely be equated with every harness's display name. [Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/create-custom-agents-for-cli), [Cursor](https://cursor.com/docs/subagents#file-locations), [omp](https://omp.sh/docs/subagent-authoring#choose-where-it-lives)
- **Tool-name translation is semantic, not capitalization.** Copilot provides explicit aliases (`Grep`/`Glob` → `search`, `Write`/`Edit` → `edit`), but `web` has no current cloud mapping. OpenCode gates several edit tools under one `edit` permission; Gemini uses names such as `read_file` and `grep_search`. Unknown names can be silently ignored in Copilot, whereas an unusable Claude list may prevent launch. Never turn an unrecognized restrictive tool policy into omitted `tools` (which often means full inherited access). [Copilot tools](https://docs.github.com/en/copilot/reference/custom-agents-configuration#tools), [OpenCode permissions](https://opencode.ai/docs/agents/#permissions), [Gemini schema](https://geminicli.com/docs/core/subagents/#configuration-schema), [Claude fields](https://code.claude.com/docs/en/sub-agents#frontmatter-reference)
- **`readonly` is not “please don't edit.”** Cursor documents a permission restriction; Codex expressly says instructions to avoid edits do not create a separate read-only sandbox. Dropping a safety field and copying its intent into prose is a degraded conversion, not equivalent support. [Cursor fields](https://cursor.com/docs/subagents#configuration-fields), [Codex approval controls](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls)
- **Do not blindly copy model strings.** Claude family aliases, OpenCode `provider/model`, omp ordered selectors/role aliases, Cursor IDs/parameters, and Codex model IDs/effort settings are different contracts. Inheritance should generally be represented by omission where appropriate, not by assuming every harness recognizes literal `inherit`. Exact model availability remains an account/provider concern. [Claude models](https://code.claude.com/docs/en/sub-agents#choose-a-model), [OpenCode models](https://opencode.ai/docs/agents/#model), [Cursor models](https://cursor.com/docs/subagents#model-configuration), [omp roles](https://omp.sh/docs/agents-and-roles#how-an-agent-gets-its-model), [Codex schema](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema)
- **Instruction inheritance differs.** Claude can omit project `CLAUDE.md` via `omitClaudeMd`; Copilot CLI subagents do not follow repository custom instructions by default and require `include-custom-instructions: true` to opt in. This changes behavior even if the Markdown body is byte-identical. [Claude fields](https://code.claude.com/docs/en/sub-agents#frontmatter-reference), [Copilot CLI instructions](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/create-custom-agents-for-cli#applying-your-repositorys-custom-instructions-to-a-custom-agent)
- **Compatibility directories are not a universal target.** Cursor listing `.codex/agents/` while describing Markdown does not establish that Codex consumes those Markdown files, or that Cursor imports every Codex TOML field. Install into each harness's native directory and format unless that exact interop path is separately verified. [Cursor locations/format](https://cursor.com/docs/subagents#file-locations), [Codex standalone TOML](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents)
- **omp documentation has an important safety nuance.** Its public authoring page calls explicit `tools` a capability boundary; its implementation notes specify that the list selects built-ins while MCP, extension, and custom tools remain additive. A registry must not advertise arbitrary omp agents as securely read-only based solely on the built-in list. [Public authoring](https://omp.sh/docs/subagent-authoring#grant-tools-safely), [implementation notes](https://github.com/can1357/oh-my-pi/blob/main/docs/task-agent-discovery.md#agent-definition-shape)

## Markdown → Codex TOML: feasible, but bounded

**Conclusion:** mechanical conversion of the common instruction/identity subset is feasible against the **current standalone-agent TOML schema**. Lossless conversion of arbitrary harness-native Markdown agents is not. Current official docs no longer require registering every standalone agent as a separate role in the root `config.toml`; do not build that extra mutation into the contract without selecting an older Codex compatibility target. [Codex custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents)

| Source concept | Codex mapping | Fidelity |
| --- | --- | --- |
| Stable name + description | `name`, `description` | Direct when values satisfy the target schema; file-derived source names must be resolved first. |
| Markdown body | `developer_instructions` TOML string | Text can be preserved exactly with a real TOML serializer. Instruction priority/runtime behavior is not identical across harnesses. |
| Model / reasoning choice | `model`, `model_reasoning_effort` and supported model options | Only with explicit target-valid mapping or author-provided Codex variant; do not silently map a Claude alias to an unrelated OpenAI model. |
| Disable shell | `features.shell_tool = false` | Documented capability reduction, not a complete generic tool-list conversion. |
| Exact tool allowlist, per-agent approval/sandbox, inline MCP | No general equivalent in the documented agent schema | Require a native alternative or report unsupported. Parent configuration owns permissions/provider/MCP; agent-local `sandbox_mode`, `approval_policy`, `model_provider`, `mcp_servers` do not override it. agnthub therefore refuses an authored Codex agent declaring `sandbox_mode = "read-only"` on Codex (it could still edit files) and installs `workspace-write`/`danger-full-access` there with a note that the session's sandbox applies; converted to the other harnesses, `read-only` withholds edit tools. |
| Hooks, worktree isolation, turn/time limits, nested-agent rules, output schema, handoff/advisor behavior | No equivalent established by this schema | Unsupported unless a separately verified Codex facility supplies equivalent behavior; prose is not enforcement. |
| Persistent memory, preloaded skills | No per-agent equivalent (`features.memories` is global; `skills.*` only disables) | Additive, not a restriction: emulated with instructions where the agent can write its notes inside the project, otherwise noted (see [persistent memory and preloaded skills](#persistent-memory-and-preloaded-skills-verified-2026-11-03)). |

The target source explicitly allows disabling `features.shell_tool`, `features.apps`, `features.plugins`, `features.memories`, and `features.request_permissions_tool`, plus skill controls. That is a finite supported list, **not** authority to copy arbitrary root-session configuration keys into an agent file. [Codex schema and inherited settings](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema)

### Concrete nonportable semantics

An OpenCode agent can deny edits and require approval for every shell command except a small allowed set:

```yaml
permission:
  edit: deny
  bash:
    '*': ask
    'git diff': allow
    'git log*': allow
```

This native policy is documented in [OpenCode's agent permissions](https://opencode.ai/docs/agents/#permissions). Codex's current custom-agent schema cannot install that equivalent **agent-local** command approval policy: it inherits the parent's sandbox/approval settings. Leaving the shell enabled broadens policy; disabling it prevents the allowed commands; writing “only run git diff/log” in instructions is not enforcement. A safe conversion must identify this incompatibility rather than claim full support. [Codex approval controls](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls) agnthub carries command patterns only where they are exact: Claude Code `Bash(<pattern>)` allowlist entries become OpenCode `permission.bash` patterns in order after `'*': deny`, and OpenCode agents keep theirs. On every other target (Claude Code too, for an OpenCode source) the shell is withheld rather than widened, and because the agent loses shell access it uses, only with the user's explicit `--allow-without-shell` ([ADR 0012](../adr/0012-portable-cores-as-claude-and-reduced-capability.md)); this example also withholds edits, so Codex refuses it outright.

Another hard semantic mismatch: an omp agent with `spawns: [reviewer]` can delegate to that specialist, but a Gemini custom subagent cannot invoke any subagent. This agent's orchestration cannot be preserved by renaming frontmatter. [omp fields](https://omp.sh/docs/subagent-authoring#frontmatter-reference), [Gemini recursion protection](https://geminicli.com/docs/core/subagents/#isolation-and-recursion-protection) Withholding delegation never widens what the agent may do, so agnthub installs such an agent on Gemini CLI without delegation and shows it as a prominent `! reduced:` plan line. A delegation limit (omp `spawns`, Copilot CLI `agents`) stays a limit only on omp; Claude Code, OpenCode, Copilot CLI and Gemini CLI withhold delegation (reduced), and Cursor and Codex, which can neither limit nor withhold it, install the agent with a note.

## Harness variants: recommended design boundary

These are **recommendations**, not upstream standards:

1. Track one registry agent identity with explicit authored variants keyed by **harness and format/version**; optionally retain a deliberately small generic Markdown source. A repository can publish several agents and several variants per agent without pretending those variants are separate roles. In practice almost every generic source (`agents/*.md`) is a Claude Code agent with `model`, `tools` and `color`, so agnthub reads a portable core's frontmatter with Claude Code's meaning and refusals ([ADR 0012](../adr/0012-portable-cores-as-claude-and-reduced-capability.md)): `model` and `permissionMode` carry to Claude Code only, `color` is dropped, `tools`/`disallowedTools` are the tool policy, and restriction-like keys Claude Code ignores, other dialects' delegation lists (`agents`, `spawns`, `subagents`, `handoffs`) and `${CLAUDE_PLUGIN_ROOT}` instructions still refuse.
2. Prefer an authored native variant over generated output. Native Markdown is still harness-specific: suffix/path, field names, model IDs, tool namespaces, inherited context, and policy are part of the variant.
3. Classify conversion results as exact/native, generated common-subset, or incompatible. Do not silently drop restrictions or claim security guarantees from prompt text. A generic-only artifact is an instruction profile, not automatically a portable sandboxed agent.
4. Keep global parent-session settings out of automatic installation. An agent installer should not quietly reconfigure Codex MCP servers/permissions, Gemini policy files, or organization-wide settings to make a variant appear supported.

## What might “OpenAgent spec” mean?

The name is ambiguous; none of these sources proves the user intends one, nor that the seven coding harnesses natively load it.

| Candidate | What its own source actually defines | Relevance / caveat |
| --- | --- | --- |
| **Oracle Open Agent Specification / Agent Spec** | Framework-agnostic language for standalone agents, structured workflows, and multi-agent composition; PyAgentSpec exports JSON/YAML. [Official docs](https://oracle.github.io/agent-spec/index.html), [Oracle repository](https://github.com/oracle/agent-spec) | Plausible intended established “Open Agent Specification”; much broader than a coding-harness persona file. Needs a chosen compatible runtime/adapter, not just a file-copy destination. |
| **`openagent-spec/spec` — OpenAgent Specification v1** | A draft `agent.yaml` / `agent.yml` universal manifest with identity, persona, model requirements, adapters, experience and marketplace metadata; source labels it `1.0.0-draft`. [Spec](https://github.com/openagent-spec/spec/blob/main/SPEC.md) | Name is the closest exact textual match. Its examples claiming framework compatibility are specification examples, not proof that Claude/Codex/etc. load the format natively. |
| **Prime Vector Open Agent Spec (OA)** | Declarative YAML task/input/output/prompt/model contracts, with its own `oa` CLI/runtime; repository example uses `open_agent_spec: '1.6.0'`. [First-party repository](https://github.com/prime-vector/open-agent-spec), [project site](https://www.openagentspec.dev/) | Another credible naming match, but a distinct format/runtime. Site and repository versions may differ; pin the selected specification instead of relying on the name. |

A2A (remote-agent communication) and MCP (tool/server connectivity) are different concerns, not interchangeable agent-definition formats. Oracle's positioning makes that distinction explicitly, and Gemini separately documents A2A remote subagents. [Oracle positioning](https://oracle.github.io/agent-spec/26.3.1/agentspec/positioning.html), [Gemini remote subagents](https://geminicli.com/docs/core/remote-agents/)

## Runtime-verified installer findings

Checked against the shipped CLIs (cursor-agent 2026.10.22-27dcf5f, Gemini CLI 0.66.0) while implementing the installers; these override documentation where they differ. The [end-to-end suite](../../CONTRIBUTING.md#end-to-end-suite) keeps checking installs against every Harness at the versions pinned in `e2e/Dockerfile` and, nightly, at each Harness's latest release.

- **Cursor reads frontmatter line by line, not as YAML.** Each `key: value` line sets a lowercased key to the raw trimmed value; quotes are kept, block scalars read as `>`/`|`, nested lines also match, and only the text `true` enables `readonly`/`is_background` (`background` is an alias). Files with an empty body are skipped. The installer therefore checks what Cursor's reader sees, not only the YAML: a quoted, commented, nested or multi-line declaration that would change identity, description or read-only mode is refused.
- **cursor-agent scans workspace `.cursor/agents` (plus `.claude/agents` and `.grok/agents`) and plugin subagents only.** It does not read `~/.cursor/agents`; user-scope installs follow the documented editor location. The e2e native check runs the same release's agent-cli-local build headless and asserts it still loads none of them, so a release that starts loading user agents is noticed.
- **Gemini CLI validates agent frontmatter strictly** (unknown keys are errors; `name` must match `^[a-z0-9-_]+$`; local agents allow `tools`, `mcp_servers`, `model`, `temperature`, `max_turns`, `timeout_mins`, `display_name`; remote agents need exactly one of `agent_card_url`/`agent_card_json`), skips files whose names start with `_`, and only loads project agents in trusted folders after the user acknowledges each new or changed file. A headless `gemini -p` run never asks, so it silently skips unacknowledged project agents. `GEMINI_CLI_HOME` replaces the home directory, so user agents live in `$GEMINI_CLI_HOME/.gemini/agents`.
- **Gemini CLI's agent-scoped MCP field is `mcp_servers`.** 0.66.0 (pinned, and the latest release on 2026-11-02) loads an agent declaring `mcp_servers` and fails one declaring the documented `mcpServers` with "Unrecognized key(s) in object: 'mcpServers'"; agnthub installs the former and refuses the latter, and the e2e suite re-checks both against every new release. Besides the Claude Code and Copilot CLI agents that declare them, Gemini CLI is the only harness with per-agent MCP servers, so agnthub converts inline agent-scoped servers (Claude Code `mcpServers`, Copilot CLI `mcp-servers`) only to Gemini's `mcp_servers` (`command`/`args`/`env`/`cwd`, `httpUrl` or `url` with `headers`, Copilot `tools` as `includeTools`) and refuses them on every other conversion target, Claude Code included for a portable core; a server referenced only by name, a setting without a Gemini equivalent, and `${{ secrets.… }}` or `${VAR:-default}` substitutions refuse Gemini too.
- **Gemini accepts `invoke_agent` in a subagent's `tools` without error but never lets a subagent invoke agents,** so agnthub refuses that declaration in a Gemini agent rather than install a delegation the Harness ignores. An agent converted from another harness that delegates installs on Gemini CLI without delegation instead, as a prominent `! reduced:` plan line.

A relative `GEMINI_CLI_HOME` resolves against the working directory; no XDG. | The working directory only, in trusted folders, with a per-file acknowledgement. In 0.66.0 a session started in `$HOME` registers `~/.gemini/agents` twice (project and user, "Duplicate agent name" warning); 0.67.0 skips the home directory as a workspace. | [subagents](https://geminicli.com/docs/core/subagents/), [trusted folders](https://geminicli.com/docs/cli/trusted-folders/); `cli/config.ts`, `core/utils/paths.js` |
| omp | `.omp/agents/*.md` | `~/<PI_CONFIG_DIR or .omp>/agent/agents`; named profile `~/<PI_CONFIG_DIR or .omp>/profiles/<profile>/agent/agents` (`--profile` > `OMP_PROFILE` > `PI_PROFILE`). `PI_CONFIG_DIR` is joined under `$HOME` even when absolute; discovery ignores `PI_CODING_AGENT_DIR` and XDG. | Walks up from the working directory to `/` and uses **only the nearest existing** `.omp/agents` (even an empty one), with no Git-root or `$HOME` stop. **The home directory is no project.** Project agent files written into `$HOME` (what agnthub 0.4.7 and earlier did when run there) land somewhere each Harness reads differently:

- omp: `~/.omp/agents` beside the user directory `~/.omp/agent/agents`. It loads as a *project* agent in every session under `$HOME` whose project has no `.omp/agents` of its own, shadows a user agent of the same name, and disappears in projects that have their own directory and in sessions started in `$HOME`.
- OpenCode: `~/.opencode/agents` (the v2 installer already creates `~/.opencode` for its binary) loads in every session under `$HOME` and outranks the user directory.
- Copilot CLI: `~/.github/agents` loads in every session under `$HOME` outside Git repositories, and in none inside them.
- Claude Code, Codex: `~/.claude/agents` and `~/.codex/agents` are the user directories (with the default config dir), so the "project" install is really a user install recorded in a project lock; with `CLAUDE_CONFIG_DIR`/`CODEX_HOME` elsewhere it loads almost nowhere.
- Gemini CLI: `~/.gemini/agents` is the user directory (same caveat with `GEMINI_CLI_HOME`); 0.66.0 also registers it twice in a session started in `$HOME`.
- Cursor: `~/.cursor/agents` loads only in a session started in `$HOME`.

So agnthub never treats the home directory, or any directory above it, as a project: `add` there installs into user scope (as `--global`) and refuses an explicit project scope (`--global=false`, MCP `scope: project`); `list`, `check`, `update`, `restore` and `remove` there use user scope too, except that a home project lock left by 0.4.7 and earlier is still listed, checked and removable there (and deleted once empty), while `update`/`restore` refuse to rewrite it. Relative `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME` and `GEMINI_CLI_HOME` refuse user-scope installs: those Harnesses resolve them against the directory they run in, so there is no single user directory. Remaining differences agnthub does not follow: the project root is the working directory (not the Git root), so an install from `repo/sub` is seen only from `repo/sub` and, on omp, shadows `repo/.omp/agents` there; `CLAUDE_CONFIG_DIR` set only in a Claude settings file and an empty `CLAUDE_CONFIG_DIR` are not read.

## Cross-harness tool mapping (runtime-verified 2026-10-30)

Checked against the installed CLIs (Claude Code 2.1.309, OpenCode v2.1.3, Codex 0.164.0, GitHub Copilot CLI 1.0.105, cursor-agent 2026.10.22, Gemini CLI 0.66.0, omp 18.13.3) with temporary homes and no model calls, plus the bundled sources. This is the table [ADR 0009](../adr/0009-cross-harness-conversion-through-shared-semantics.md)'s converters implement.

| Capability | Claude Code `tools` | OpenCode `permission` | Copilot CLI `tools` | Gemini CLI `tools` | omp `tools` | Codex | Cursor |
| --- | --- | --- | --- | --- | --- | --- | --- |
| read | `Read` (`LSP`) | `read` | `read` (`view`) | `read_file`, `list_directory` | `read` (also fetches URLs) | always | always |
| search | `Grep`, `Glob` | `glob`, `grep` | `search` (`grep`, `glob`) | `glob`, `grep_search` (`search_file_content`) | `grep`, `glob`, `find` | always | always |
| edit | `Edit`, `Write` (`NotebookEdit`) | `edit` (covers write/patch) | `edit` (`create`, `edit`) | `replace`, `write_file` | `edit`, `write` | always | off only with `readonly: true` |
| shell | `Bash` (`PowerShell`, `TaskStop`) | `bash` (V2 `shell`) | `execute` (`shell`, `bash`) | `run_shell_command` | `bash` (`exec`, `eval`) | off with `features.shell_tool = false` | off only with `readonly: true` |
| web fetch | `WebFetch` | `webfetch` | `web` (only `web_fetch`) | `web_fetch` | `read` | session | not withholdable |
| web search | `WebSearch` | `websearch` | none | `google_web_search` | `web_search` | session | not withholdable |
| delegation | `Agent` (`Task`) | `task` (V2 `subagent`) | `agent` (`task`) | none: subagents cannot invoke agents | `task` | session | not withholdable |
| MCP | `mcp__server__tool`, `mcp__server__*` | `<server>_<tool>`, `<server>_*` (plus `execute`) | exposed `<server>-<tool>` only | `mcp_<server>_<tool>`, `mcp_<server>_*` | always additive | inherited | blocked by `readonly` |

- **Claude Code.** `Task` is an alias of `Agent`; `MultiEdit`, `LS`, `NotebookRead`, `TodoRead`, `BashOutput` and `TaskOutput` no longer exist and grant nothing. Glob and Grep only appear for agents without `Bash` (the shell searches through embedded tools). `SendMessage` messages other Claude Code agents and sessions; no other harness can address them, so conversion drops it with a note. `Agent(a, b)` limits spawn types only for a main-session agent. `tools` accepts a list or a comma/space string; `*` or omission inherits everything. Unknown fields are ignored. Fields: `name`, `description`, `tools`, `disallowedTools`, `model`, `effort`, `permissionMode`, `mcpServers`, `hooks`, `maxTurns`, `autoCompactWindow`, `skills`, `initialPrompt`, `memory`, `background`, `omitClaudeMd`, `isolation`, `color`. A file with `tools: Read, Grep, Glob` loads with exactly those tools.
- **OpenCode V2.** Rules are `{action, resource, effect}` with the last match winning, after built-in defaults (`* allow`, `read *.env`/`*.env.*` ask, `*.env.example` allow). A V1 `permission` map is still read (`bash`→`shell`, `task`→`subagent`, `write`/`patch`→`edit`); key order is preserved, so an allowlist writes `"*": deny` first. `"*": deny` also hides MCP tools, `question` and `subagent`. Conversion repeats the `.env` defaults under `read`, since `read: allow` would otherwise override them. Never mix V1 keys (`tools`, `permission`, `name`) with the V2 `permissions` list in one file: OpenCode then reads it as V1 and silently drops the list.
- **Copilot CLI.** Aliases are case-insensitive; unknown names are ignored; `skill` and `sql` are always present (even with `tools: []`). There is no nameable web search tool: `web` and `WebSearch` only yield `web_fetch` (see [Copilot CLI cannot grant web search](#conversions-that-never-loosen-a-restriction-runtime-verified-2026-11-05) for the 2026-11-05 check of the remaining candidates). Copilot CLI also loads a project's `.claude/agents/*.md` directly (never `~/.claude/agents`) but does not translate `Agent(...)` or `mcp__…` entries.
- **Gemini CLI.** Unknown tool names fail the whole agent; wildcards are only `*`, `mcp_*` and `mcp_<server>_*`. `read_many_files` is a valid name but not registered in 0.66. `invoke_agent` and `update_topic` are always stripped from subagents; `complete_task` is always added. Project agents also need a per-file acknowledgement keyed by SHA-256 in `$GEMINI_CLI_HOME/.gemini/acknowledgments/agents.json`.
- **omp.** Built-in names match case-insensitively and unknown names are silently dropped; `tools: []` grants no built-ins; MCP, extension and custom tools stay additive whatever `tools` says. `read` without `write` adds a device-only `write` that cannot write project files.
- **Codex.** Only `developer_instructions`, the model keys, `personality`, `service_tier`, disable-only `features.{shell_tool, apps, plugins, memories, request_permissions_tool}` and disable-only `skills.*` take effect when a custom agent spawns. `web_search = "disabled"` and `sandbox_mode` parse but are ignored; the parent session's sandbox, web search and MCP servers always apply. Project agents load only from a trusted project (`[projects."<path>"] trust_level = "trusted"` in `$CODEX_HOME/config.toml`). agnthub reads an authored agent's `sandbox_mode` and `features.multi_agent = false` as declared restrictions: on Codex, `read-only` is refused and the others install with a note that the session's sandbox applies, and `multi_agent = false` installs with a warning that Codex does not enforce it; converted elsewhere, `read-only` withholds edits and `multi_agent = false` withholds delegation.
- **Cursor.** `readonly: true` blocks writes, deletes, every shell command (not only state-changing ones, unlike the docs) and MCP tool calls; reads, searches and web fetch/search stay available. It is Cursor's only restriction, so agnthub converts an agent without edits to `readonly: true`: MCP tools it uses are lost (a `! reduced:` plan line), a shell it uses is lost too, which installs only with `--allow-without-shell`, and an agent that edits but withholds the shell stays refused. A `tools` line is sent to the server but not enforced by the client, so it is not a supported restriction: an authored Cursor agent with `tools` installs on Cursor as written with a warning, and other harnesses enforce it as a Claude Code allowlist.
- **MCP tool names (runtime-verified 2026-10-30 against fake MCP servers and a local fake model endpoint).** OpenCode checks the permission `<server>_<tool>` (non `[A-Za-z0-9_-]` replaced by `_`, `*` globbing) and by default lists MCP tools only inside its Code Mode `execute` tool, which also offers `fetch`: an agent with `"*": deny`, `execute: allow` and `context7_query-docs: allow` saw only context7's tools. Copilot CLI 1.0.105 exposes `<server>-<tool>` (non `[A-Za-z0-9_-]` replaced by `-`, cut at 64 characters) and a tools list grants an MCP tool only by that name, case-insensitively; the documented `server/tool`, `server/*` and `server-*` entries granted nothing for session servers. Gemini CLI registers `mcp_<server>_<tool>` (cut beyond 63 characters), parses the server up to the first `_` for validation and `mcp_<server>_*`, and a subagent listing `mcp_github_get_commit` and `mcp_github_pull_request_read` received exactly those two of the configured MCP tools. omp gave a `tools: [read, grep, glob, find, bash]` subagent every configured MCP tool. Claude Code names plugin servers `plugin_<plugin>_<server>` and splits `mcp__` names at the first `__`.

## Persistent memory and preloaded skills (verified 2026-11-03)

Checked against the installed CLIs (Claude Code 2.1.309, OpenCode 2.1.3, Codex 0.164.0, Copilot CLI 1.0.105, cursor-agent 2026.10.22-27dcf5f, Gemini CLI 0.66.0, omp 18.16.0, which matches the pinned 18.13.3 for these questions) and their first-party docs, with temporary homes. This is the table [ADR 0009](../adr/0009-cross-harness-conversion-through-shared-semantics.md)'s additive rule implements.

**What Claude Code does.** `memory: user | project | local` gives the subagent a persistent folder: `~/.claude/agent-memory/<name>/`, `.claude/agent-memory/<name>/` or `.claude/agent-memory-local/<name>/`. The name is sanitized: characters other than `[A-Za-z0-9_-]` become `-`. Any other value is ignored with a warning. With auto memory on (the default), Claude Code then does three things. It appends a "Persistent Agent Memory" section to the agent's system prompt, with the folder, the memory types (user, feedback, project, reference), the two-step save (one topic file per memory plus a one-line pointer in the `MEMORY.md` index), what not to save, and a guideline line per scope. It injects the first 200 lines / 25 KB of `MEMORY.md`. And it adds Read, Write and Edit to an explicit `tools` list. Project and local folders must resolve inside the working copy. [Claude persistent memory](https://code.claude.com/docs/en/sub-agents#enable-persistent-memory), confirmed in the 2.1.309 binary. `skills: [...]` injects the full content of up to 32 distinct skills as a hidden message before the task. Missing, disabled or non-prompt skills are skipped with a debug warning, and the Skill tool is not needed. [Claude preloaded skills](https://code.claude.com/docs/en/sub-agents#preload-skills-into-subagents)

agnthub's rule (ADR 0009), per target:

- **Memory.** No target has a per-agent equivalent, so memory is emulated only where the converted agent can already read and edit files. A short section delimited by `<!-- agnthub: persistent memory … -->` and `<!-- /agnthub -->` is appended to the agent's instructions. It mirrors Claude Code's template: the folder, read `MEMORY.md` at the start, one file per memory plus a one-line pointer in `MEMORY.md` (under 200 lines), what not to save, and Claude's guideline line for the scope.
  - Project and local scope use Claude Code's own folders on every target, so an agent installed on Claude Code and elsewhere shares its notes. `.agents/` would be read-only on Codex.
  - User scope uses `~/.claude/agent-memory/<name>/` on OpenCode and omp, and `~/.cursor/agent-memory/<name>/` on Cursor. OpenCode allowlists add `external_directory` for exactly that folder.
  - User scope is noted and dropped on Codex, Copilot CLI and Gemini CLI, whose agents cannot write outside the project without an approval that headless runs never give.
  - An agent without edits keeps its tools and is noted: memory never grants tools.
- **Skills.** Native on Claude Code (`skills`), Copilot CLI (`skills`) and omp (`autoload-skills`). Elsewhere a delimited section tells the agent to load the named skills before it starts: OpenCode via `skill`, Gemini CLI via `activate_skill`, Codex and Cursor by reading the listed `SKILL.md`. OpenCode and Gemini CLI allowlists also gain their skill tool, a session helper that changes nothing the agent can affect. Every target notes that the skills must be installed for it: the field never installs them; Skill Dependencies stay a manifest feature.

**Keys Claude Code ignores (verified 2026-11-03).** Claude Code 2.1.309 recognizes exactly the 19 fields of its [frontmatter reference](https://code.claude.com/docs/en/sub-agents#frontmatter-reference) (`name`, `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `autoCompactWindow`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `omitClaudeMd`, `effort`, `isolation`, `color`, `initialPrompt`, `experimental`). `claude --debug` logs every other top-level key, offline, as `Agent file <path> has frontmatter keys Claude Code does not recognize or apply: "capabilities", "category", "allowed-tools" (did you mean "tools"?)` (up to five per file); `prompt` is ignored in files too. Turn limits: only Claude Code, OpenCode (`steps`) and Gemini CLI (`max_turns`) have a per-agent limit.

## Conversions that never loosen a restriction (runtime-verified 2026-11-05)

The refusal census of the registry found refusals that are safe to lift because the harness that wrote the file ignores the field, because dropping it only asks for more approval, or because the only faithful alternative withholds a capability the target cannot grant, which never widens what the agent may do ([ADR 0012](../adr/0012-portable-cores-as-claude-and-reduced-capability.md): such a reduction is a prominent `! reduced:` plan line, and losing shell access the agent uses needs `--allow-without-shell`). Each was checked against the pinned CLIs in the e2e images (Claude Code 2.1.309, Codex 0.164.0, Copilot CLI 1.0.105, cursor-agent 2026.10.22-27dcf5f) and their first-party docs.

- **Claude Code hook events are exact and case-sensitive.** The agent loader keeps the 33 events of the [hooks reference](https://code.claude.com/docs/en/hooks#hook-lifecycle) and drops every other key of an agent's `hooks` with `Agent '<name>': hooks.<key>: unknown hook event; entry ignored`, the agent still loading: `pre`/`post` (a widely copied template's shell snippets), `notification`, `post_edit`, and `preToolUse` even with a matcher list. It refuses to load the agent (`not loaded: … holds PreToolUse/PermissionRequest hooks`) when an unknown key holds `PreToolUse`/`PermissionRequest` hooks or a matcher map with `hooks`, when `hooks` is itself a matcher, and when `hooks` is a string, number, boolean or list (`expected record`). agnthub mirrors that reader: `hooks` whose every key is ignored converts with `omitted hooks: Claude Code ignores these events (post, pre)`; any real event, or a shape Claude Code refuses, still refuses. The e2e suite checks Claude Code still logs each omitted event as unknown, and a nightly test compares the event list with the reference.
- **Permission modes that only relax approvals.** For subagents, `acceptEdits` auto-accepts edits, `auto` lets a classifier approve in the user's place, and `bypassPermissions` skips prompts ([permission modes](https://code.claude.com/docs/en/sub-agents#permission-modes)); a step the classifier blocks can always be approved from a prompt in Manual mode. None withholds anything, so converting to a harness that asks for approval as its session does is at least as strict: the mode is dropped with `permissionMode acceptEdits isn't available in <harness>; the harness asks for approval as usual`. `plan` restricts the agent to read-only tools, so it converts as a read-only tool policy (no edits, shell, delegation or MCP tools, since a delegated agent or an MCP tool could write; each one the agent used is a reduction): Claude Code keeps the mode, Codex refuses it (no way to withhold edits), and an agent whose tools include the shell loses it there, with the opt-in, because no other harness can limit the shell to read-only commands. `dontAsk` (auto-deny anything that would prompt) stays refused; modes are case-sensitive.
- **Claude Code matches `tools` names exactly and grants nothing for unknown ones.** Run against a stub model API, an agent with `tools: read, grep, glob, edit, write, bash` (or `All tools`, or `Foo, Bar`) sent no tools at all, `Read, Grep` sent Read and Grep, and `Read, ListMcpResourcesTool, SlashCommand, playwright` sent only Read. So the lowercase names other harnesses use are not aliases in a Claude Code file, and agnthub adds none: mapping them would grant tools Claude Code never gave. Allowlisted names with no equivalent are left out with a note on every target, which only withholds them; unknown names in a denylist still refuse.
- **Cursor keeps a frontmatter value as written.** Run against a stub model, cursor-agent-local listed `'Use it: for the session''s effort'` and `"…\"quoted\"…"` verbatim, quotes and escapes included, and a block scalar as `>-`. Conversion writes the description's words on one line: plain when YAML allows, else quoted with the fewest escapes, which the e2e native check decodes as YAML. An authored Cursor agent whose description spans lines installs with only its description lines rewritten, when Cursor reads every other key as declared.
- **Documentation keys.** Copilot CLI 1.0.105 lists agents declaring `color`, `title`, `kind`, `emoji`, `status`, `owner` and similar keys it does not define, and documents that unrecognized tool names are ignored; Cursor reads only its own keys. Both install such Variants as written with a note. Codex 0.164.0 loads only agent files whose keys it defines (`author` or `color` skip the file) and reads `nickname_candidates` as display names: a non-empty list of distinct names of ASCII letters, digits, spaces, hyphens and underscores (`["Ada!"]` or `[]` skip the file). Gemini CLI rejects unknown keys, so `color` keeps a Gemini variant invalid. Restriction-like keys a harness ignores and no other harness can read as a restriction (`readonly` in a Claude Code agent, `permission`, `allowed-paths`…) stay refused.
- **Restrictions their own harness ignores.** Claude Code ignores `allowed-tools` in agents (a skill field; `claude --debug` lists it as unrecognized, see above), Cursor does not enforce `tools`, Copilot CLI 1.0.105 ignores `agents`, `allowed-tools` and `maxTurns` in its agents, and agnthub treats Codex `features.multi_agent` in an agent file as unenforced: the agent keeps the session's subagents. Refusing them hid agents whose restriction other harnesses can enforce, while installing them on their own harness changes nothing the author got there. So each installs on its own harness as written, with a warning that the harness does not enforce it, and is honored elsewhere where it can be expressed: `allowed-tools` and Cursor `tools` as the tool allowlist (intersected with `tools`), Copilot `agents` as omp `spawns` (delegation withheld on Claude Code, OpenCode, Copilot CLI and Gemini CLI; noted on Cursor and Codex, which cannot withhold it), `maxTurns` as a turn limit, and `multi_agent = false` as no delegation.
- **Copilot CLI cannot grant a custom agent web search.** Run against Copilot CLI 1.0.105 with a temporary home and a real account (one model call): a `web_search` entry in an agent's `tools` grants nothing; `github-mcp-server/web_search` makes Copilot ask GitHub's MCP server for a tool it does not offer, and the agent ends with only `view`, `skill` and `sql`; `api.githubcopilot.com/mcp/` offers no `web_search` across all 117 tools of all its toolsets; and an agent with no tool limits gets 28 tools, none of them web search. An allowlist granting web search therefore installs on Copilot CLI without it (web fetch stays as `web`), as a `! reduced:` line rather than a refusal.
- **Native loading of the newly installed shapes (e2e native checks, 2026-11-05).** Codex 0.164.0 loads agent files declaring `sandbox_mode = "workspace-write"` or `[features] multi_agent = false`: `codex debug prompt-input` lists both as spawn roles in project and user scope. Gemini CLI 0.66.0 loads an agent converted from a Claude Code `mcpServers` declaration into its own `mcp_servers` (`command`, `args`) with an `mcp_<server>_<tool>` entry, in project (acknowledged) and user scope, without an agent loading error. The suite re-checks both against every pinned and latest release.
- **Background agents.** agnthub carries background execution only to Claude Code (`background`) and Cursor (`is_background`); running the agent in the foreground on the other harnesses blocks the caller but withholds nothing, so those installs carry a note instead of refusing.

## Manual-only invocation and worktree isolation (verified 2026-11-06)

Checked against the live first-party docs and the CLIs pinned in the e2e images (Claude Code 2.1.309, OpenCode 2.1.3, Codex 0.164.0, Copilot CLI 1.0.105, cursor-agent 2026.10.22-27dcf5f, Gemini CLI 0.66.0, omp 18.13.3), with offline runs in throwaway containers (temporary `HOME`, a local model stub that logs requests). agnthub's mapping is [ADR 0014](../adr/0014-emulate-worktree-isolation-and-manual-only-invocation.md).

**Whole-tool wildcard.** Claude Code documents "`Bash(*)` is equivalent to `Bash` and matches all Bash commands" ([permissions](https://code.claude.com/docs/en/permissions#match-all-uses-of-a-tool)), and 2.1.309's rule parser returns the bare tool for any tool when the content is empty or exactly `*` (`if(n.rawContent===""||n.rawContent==="*")return{toolName:…}`). agnthub reads `WebFetch(*)`, `Bash(*)`, `Read(*)`… as the plain tool; any other content stays a scope.

**Manual-only invocation** (the model never delegates to the agent; the user selects it):

| Harness | Native equivalent | Evidence |
|---|---|---|
| Copilot CLI | `disable-model-invocation: true`; the retired `infer: false` means the same, and `disable-model-invocation` wins when both are set | [Copilot agent fields](https://docs.github.com/en/copilot/reference/custom-agents-configuration): "When `true`, the agent must be manually selected". Runtime: such an agent loads (`--agent missing` lists it) and `--agent <it>` runs, but the model's `task` tool lists only the other agents. |
| OpenCode | `mode: primary` (not `hidden: true`, which the subagent tool does not check and which hides the agent from the user too) | [OpenCode agents](https://opencode.ai/docs/agents): "primary — Runs as the main agent for a session"; "When omitted on a new custom agent, it defaults to `primary`". Binary: the subagent tool refuses `mode==="primary"` ("cannot run as a subagent") and its catalog filters primary agents out. Runtime: `opencode debug agents` resolves the agent as `primary`; the `subagent` tool's catalog omits it; `opencode run --agent <it>` runs it. |
| Claude Code | none: `disable-model-invocation` exists only for skills and commands | [Subagent frontmatter](https://code.claude.com/docs/en/sub-agents#frontmatter-reference) has no such field; `claude --debug` reports it as a key it does not recognize or apply. Only a settings rule (`permissions.deny: ["Agent(<name>)"]`) blocks delegation, and it is not part of the agent file. |
| Codex | none | The [custom agent schema](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema) has no such key, and Codex 0.164.0 silently skips an agent file with any unknown key (`hidden`, `isolation`, `disable_model_invocation` each tested). |
| Cursor | none | [Cursor subagents](https://cursor.com/docs/subagents#configuration-fields): "Agent reads this [description] to decide delegation"; unknown keys are ignored. |
| Gemini CLI | none | [Gemini subagents](https://geminicli.com/docs/core/subagents/): the schema is strict (an unknown key fails the agent with `Agent loading error`), and even `@agent` asks the model to call the agent's tool. |
| omp | none | [omp frontmatter](https://omp.sh/docs/subagent-authoring#frontmatter-reference) has no such field; `task.disabledAgents` is a setting that also takes the agent from the user. |

Where there is none, delegating models choose agents by their description, so agnthub starts the description with "Use only when the user explicitly asks for this agent." and shows the loss as reduced (`manual-only invocation`).

**Worktree isolation** (the agent runs in its own git worktree, as set by its definition):

| Harness | Native equivalent | Evidence |
|---|---|---|
| Claude Code | `isolation: worktree` | [Subagent frontmatter](https://code.claude.com/docs/en/sub-agents#frontmatter-reference): "Set to `worktree` to run the subagent in a temporary git worktree, giving it an isolated copy of the repository". 2.1.309 also accepts an undocumented `remote` (a cloud environment), which agnthub keeps refusing elsewhere, and logs `has invalid isolation value` for other values. |
| OpenCode | none | No agent key or `subagent` tool parameter; its worktrees are per workspace. |
| Codex | none | Only a session-wide `codex --worktree`; `spawn_agent` takes no isolation parameter; an `isolation` key skips the agent file. |
| Copilot CLI | none | Only a session-wide `--worktree`; the `task` tool has no isolation parameter. |
| Cursor | none per agent | [Cursor subagents](https://cursor.com/docs/subagents): "Subagents share the parent agent's checkout by default. … Ask for isolation and each subagent runs in its own copy"; isolation is per request or a session-wide `--worktree`, not an agent field. |
| Gemini CLI | none | Only a session-wide `--worktree` behind `experimental.worktrees`; an `isolation` key fails the agent. |
| omp | none per agent | [omp subagent authoring](https://omp.sh/docs/subagent-authoring): "Isolation is chosen for an individual delegation, not in agent frontmatter"; the delegating model sets `isolated: true` per task, only when the user enabled `task.isolation.enabled`. |

Where there is none, an agent with an unrestricted shell is told at the top of its instructions to create a git worktree (`git worktree add …`), make every edit, command and commit there and report the worktree path and branch, and the loss shows as reduced (`isolation`). An agent that edits without such a shell cannot create one and stays refused there; one that neither edits nor runs commands needs no isolation.

## Decisions and remaining unknowns

1. **Exact product support target:** CLI-only, IDE, or cloud per harness? Copilot especially needs separate surface labels. Should initial support include all seven, or only a tested subset? Skill support is not agent support.
2. **Canonical authoring contract:** tiny generic name/description/instructions profile, native files only, or both? If both, must generic content generate a named harness variant or only supply fallback instructions?
3. **Conversion policy:** reject unsupported semantics, require native variants, or permit an explicitly opted-in degraded installation? Recommended default: reject dropped safety constraints, with no silent permission expansion. Decided in [ADR 0012](../adr/0012-portable-cores-as-claude-and-reduced-capability.md): a restriction is still never loosened; a capability the target cannot grant is withheld with a prominent `! reduced:` plan line, and losing shell access the agent uses (Cursor `readonly`, scoped shell rules outside OpenCode, `permissionMode: plan`) needs the explicit `--allow-without-shell`.
4. **Model ownership:** inherit the user's model by default, require author-pinned models, or support install-time model mapping? Upstream aliases and availability are not portable.
5. **Identity/scope/collisions:** choose project versus user installation, stable registry IDs versus harness names, overwrite policy, and behavior when an existing higher-priority agent shadows an installed one. Native precedence is not consistent.
6. **Dependencies and executable configuration:** decide whether agent packages may include skills, MCP definitions, hooks, policy files, or scripts. These are not just harmless Markdown; installing their definitions must not imply authorizing execution or mutating parent permissions.
7. **Version compatibility:** specify minimum harness versions and whether older Codex role/config-file formats are in scope. This research establishes current documentation, not historical behavior or runtime-tested support. Cursor's Codex compatibility parsing details remain unverified.
8. **OpenAgent identity:** obtain the exact upstream URL and version before committing to any future “OpenAgent” compatibility. The three candidates above are different systems.
9. **Source inconsistencies to resolve during adapter work:** Copilot's shared reference describes `model` broadly while its cloud creation instructions emphasize model configuration for IDEs; this research does not promise cloud model pinning. omp's public tool-boundary wording is broader than its implementation notes about additive tool surfaces. Preserve these caveats in compatibility claims until implementation-specific behavior is checked.
