# Treat dependencies as installation requirements and keep setup execution out of repositories

Agents may require other agents and skills to be installed. These are presence requirements, not a promise of runtime delegation or invocation support. Installation resolves and previews the full transitive dependency closure, rejecting dependency cycles and unsatisfied requirements before applying the plan; optional native orchestration fields remain subject to the separate conservative-conversion policy.

Use skills.sh as the default skill backend, with a replacement executable and argument array controlled by the user's `~/.config/agnthub/config.yaml`. agnthub independently verifies known on-disk layouts after installation rather than trusting exit code zero or requiring a structured external backend protocol. Custom backends are consequently limited to layouts agnthub can inspect. Sources declare dependency data, not install hooks or arbitrary commands. The configured backend is trusted code; this boundary does not sandbox it, the installed agent, or future skill execution. The [CLI contract](../cli-contract.md#skill-installer-configuration-contract) defines configuration fields and literal argument substitution.

Skill requirements are unbounded by default and identify a source and skill. Optional `minVersion`/`maxVersion` bounds use strict semantic versions declared in the skill's own `SKILL.md` `metadata.version`, checked against installed content/provenance; missing or non-semver versions cannot satisfy a bounded requirement. Do not infer per-skill versions from repository tags or folder names. Reuse compatible installed skills and stop for explicit resolution rather than silently replacing incompatible existing content. This is an agnthub convention over optional skill metadata, not a universal Agent Skills versioning contract.

Both version bounds are inclusive; prereleases require explicit prerelease bounds. Validate the installed skill or the explicitly selected source revision (default revision if unspecified), rather than searching historical revisions. Reuse a verified visible installation across scopes, accounting for local shadowing, without acquiring ownership.

Backend configuration uses an executable and argument array with literal argument substitution, not implicit shell evaluation. Preflight requirements, then install and verify skills before committing dependent agent artifacts. Backend or verification failure leaves dependent agent files unchanged and reports any backend-created effects; rollback of an arbitrary configured installer is not guaranteed.
