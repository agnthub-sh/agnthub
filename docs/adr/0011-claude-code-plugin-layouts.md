# Discover the agents of Claude Code plugins a repository packages

Large agent collections are published as Claude Code plugin marketplaces: `.claude-plugin/marketplace.json` lists plugins in subdirectories, each with a `.claude-plugin/plugin.json` whose `agents` field lists its agent files, or an `agents/` directory. Discovery read none of it, so such repositories offered no agents. What Claude Code does with these files is recorded in [Claude Code plugins](../research/claude-code-plugins.md).

Without `agnthub.yaml`, discovery now also reads the plugins a repository packages:

- **Which plugins.** Every `marketplace.json` entry whose `source` is a relative path inside the repository (`./dir`, `.`/`./` for the root, or a bare name under `metadata.pluginRoot`), plus the repository root when it has its own `.claude-plugin/plugin.json`. A plugin root listed twice is read once. Remote sources (`github`, `url`, `git-subdir`, `npm`, `archive`, `command`) are never fetched; each is reported as a discovery problem naming the source, so `--list` shows what the marketplace offers elsewhere. A source that does not start with `./`, is absolute, leaves the repository, is missing or is not a directory is a problem, not a failure.
- **Which agents.** The plugin's `agents` field (one path or an array; from `plugin.json`, plus a strict marketplace entry's own `agents`, or the entry's alone when the plugin has no `plugin.json`) replaces the default scan, as in Claude Code. Every path must start with `./`, stay inside the plugin root and name a `.md` file; anything else is a problem. Without the field, every `.md` file under the plugin's `agents/` is read, recursively. A `strict: false` entry that declares agents beside a `plugin.json` is reported as the conflict Claude Code refuses to load.
- **Inert and bounded as before.** Links and submodules are skipped, never followed (a source or listed path through a link is skipped too). Manifests and agent files count against the same entry, file, byte and candidate budgets; an invalid manifest is a problem and the rest of the repository is still discovered.
- **Claude Code Variants.** A plugin agent is a Claude Code native file, so it becomes the Claude Code Variant of its logical agent exactly like a `.claude/agents/` file: identity from its frontmatter `name` (required, as for other Claude Code Variants), conversion to the other harnesses through the shared semantics ([ADR 0009](0009-cross-harness-conversion-through-shared-semantics.md)). The `<plugin>:` scope Claude Code adds is not part of the identity, because an installed file is not in a plugin. A file a plugin claims is not also read as a portable definition: a root plugin's `agents/` holds Claude Code agents.
- **Duplicates.** Two plugin files, or a plugin file and a `.claude/agents/` file, with the same identity are ambiguous like any two Claude Code files (refused until `agnthub.yaml` chooses), **unless their bytes are identical**: collections often ship one agent in several plugins or also in `.claude/agents/`, and identical copies install the same file. The first copy wins, native directories before plugins, then marketplace order. A plugin whose agents are a native directory's files adds nothing.
- **Precedence.** `agnthub.yaml` stays authoritative: when present, plugins are not read. Portable and native layouts are unchanged; plugin agents add to the inventory. The lock's `sourcePath` is the plugin file's repository path.

**Fields plugins ignore are omitted, with a note.** Claude Code ignores `permissionMode`, `hooks`, `mcpServers` and `initialPrompt` in plugin agents, and documents copying the file into `.claude/agents/` as the way to activate them. Installing a plugin agent unchanged would therefore activate behavior the plugin form never had, which ADR 0002's conservative rule forbids. Refusing would make agents unavailable for fields that never took effect. So a plugin agent installs as the plugin delivers it: those keys are removed from the frontmatter by deleting only their lines (every other byte is kept, and the edit is checked by re-parsing; a header that cannot be edited that way refuses the Variant), and the plan notes each omission and that it would take effect standalone. Conversion to other harnesses starts from the same effective file, so these fields no longer refuse a plugin agent's conversion. A file outside a plugin keeps them as before.

**Agents that need their plugin are refused.** An agent whose instructions use `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` or `${user_config.…}` depends on files or settings that exist only where the plugin is installed, and nothing substitutes them in an installed agent. Its Claude Code Variant is invalid, so it is refused for every harness rather than installed broken.

`--list` (and `--list --json`'s optional `plugin` field) and the interactive picker name the plugin an agent's Claude Code Variant comes from; `--agent <id>` is unchanged.

Consequences: marketplace-packaged collections are indexable and installable with no change by their authors. Agents only reachable through remote plugin sources stay unavailable until that source is added itself. Identities the plugin scope used to keep apart (two plugins with different `reviewer` agents) are ambiguous until the repository adds `agnthub.yaml`. Identifiers Claude Code allows but agnthub does not (for example with a `.`) remain refused as invalid identifiers.
