# Convert native agents across harnesses through a shared semantics model

Most published agents exist only as one harness's native file (typically `.claude/agents/*.md`). Converting only from the portable core left them installable on that one harness, even when every other harness can express what they declare. Conversion now goes through one harness-neutral **Semantics** model: identity, description, instructions, a model hint, a tool policy over capabilities (read, search, edit, shell, web fetch, web search, delegation, todo list, skills, plus MCP and unknown tool names), turn limit, background execution, harmless omissions and unsupported behaviors. Every adapter parses its native format into Semantics and renders Semantics into its native format.

For a target harness without an authored Variant, sources are tried in a fixed order: the portable core, then every other authored Variant, Claude Code first and the rest in display order. The first source the target can represent wins; otherwise the first refusal is reported. An authored Variant for the target is still installed as is, and an invalid one still never falls back ([ADR 0002](0002-agent-variants-and-conservative-conversion.md)).

Mapping keeps ADR 0002's conservative rule. Identity, description and instructions always carry. Cosmetic fields and session helpers that grant nothing elsewhere (for example Claude's `color` or `SendMessage`) are omitted with a note. Model strings are never carried: the converted agent uses the target's default model and the plan says so. Tool allowlists translate per capability; an allowlist granting a capability the target lacks (delegation for Gemini, web search for Copilot CLI) is refused. Excluding a boundary capability (reads, searches, edits, shell) the target cannot withhold is refused; network tools, delegation and inherited MCP servers that a target cannot withhold are noted, because they never change files themselves. Behavioral and safety fields with no target equivalent (hooks, permission modes, scoped MCP servers, isolation, approval prompts, scoped tool rules) are refused; background execution maps where the target has it. A turn limit maps where the target has one (Claude Code `maxTurns`, OpenCode `steps`, Gemini CLI `max_turns`); elsewhere, by the user's decision, the agent installs with the limit as a delimited instruction (finish within about N turns, otherwise stop and report) and the note "turn limit of N isn't enforced on <harness>". Claude Code frontmatter keys outside its documented field list (pinned for 2.1.309 from the [frontmatter reference](https://code.claude.com/docs/en/sub-agents#frontmatter-reference)) are keys Claude Code itself ignores, so they are omitted with the note "omitted <key>: Claude Code ignores it". This is not a blanket drop of unknown fields: an ignored key that reads as a tool or permission restriction (`allowed-tools`, `readonly`, `permissions`, spellings of `disallowedTools`, `maxTurns` and similar) is still refused, the e2e suite checks Claude Code's own debug log names every omitted fixture key as unrecognized, and a nightly test compares the pinned list with the current reference. Every generated file is validated with the target's own Variant validator before it is offered.

Additive capabilities are not constraints. Persistent memory (Claude Code's `memory`) and preloaded skills (`skills` on Claude Code and Copilot CLI, `autoload-skills` on omp) add to what an agent knows, never to what it may do, so leaving them out never widens its permissions. They never refuse a conversion. Each target carries them in one of three ways:

1. **Native field.** Where the target has a per-agent equivalent with the same meaning, the converter writes it: `skills` on Claude Code and Copilot CLI, `autoload-skills` on omp. No other harness has per-agent memory.
2. **Instructions.** Otherwise the converter appends a short section to the instructions, delimited by `<!-- agnthub: … -->` and `<!-- /agnthub -->`.
   - Memory gets a section that mirrors Claude Code's own memory prompt: the agent's notes folder, plus `MEMORY.md` as an index read at the start. This happens only when the converted agent can already read and edit files in that folder. Project and local scope use Claude Code's own folders, so the notes are shared with Claude Code. User scope applies only where the target lets agents write under the home directory without an approval.
   - Skills get a section naming the skills to load. Where an allowlist would hide the target's skill tool, that tool is added; it is a session helper.
3. **Note only.** Otherwise the field is dropped and the plan says so: the agent starts without its notes or skills.

Every outcome other than a native field is noted in the plan and in `--json`. Memory never grants tools. The skills field never installs skills: the notes say they must be available, and Skill Dependencies remain a manifest feature. The per-target mapping and its evidence are in [harness agent formats](../research/harness-agent-formats.md#persistent-memory-and-preloaded-skills-verified-2026-11-03).

Generated artifacts record converter `<harness>/v4`. Each converter version renders what its predecessors converted byte for byte (v2 added native Variant sources, v3 MCP tool references, v4 persistent memory and preloaded skills), so locks written by v1 through v3 restore unchanged; a regenerated digest mismatch is reported as a converter change rather than substituted. The registry's assessment version is bumped so every indexed repository is re-assessed on its next refresh.

MCP tool references (`mcp__<server>__<tool>`, or a whole server) translate to each target's own MCP tool name where the target can list them per agent: OpenCode `<server>_<tool>` permissions plus its Code Mode `execute` action, Copilot CLI's exposed `<server>-<tool>` names, Gemini CLI `mcp_<server>_<tool>`, Claude Code `mcp__<server>__<tool>`. omp, Codex and non-read-only Cursor agents already keep every session MCP tool whatever their tool list says, the residual surface every converted allowlist on them carries, so an agent naming MCP tools converts there with that surface noted rather than refused. A name the target cannot address (a whole server for Copilot CLI, a Gemini or Copilot name beyond its length limit, an OpenCode permission that would also match a built-in action, MCP tools on a read-only Cursor agent) is refused. Every plan names the MCP servers the agent needs; agnthub never installs or edits MCP server configuration. Claude Code plugin servers (`plugin_<plugin>_<server>`) are named by their server name, and Claude Code's built-in `ide` connection is omitted with a note.

Consequences: native-only agents become installable wherever their declared semantics fit, with the omissions and residual surfaces stated in the plan. The capability model is the unit of translation (an allowlist naming Edit but not Write grants edits as a whole, noted), so per-tool or per-command nuance beyond it still requires an authored Variant. Harness tool vocabularies are pinned to the CLI versions in [harness agent formats](../research/harness-agent-formats.md) and need revisiting when those harnesses change.
