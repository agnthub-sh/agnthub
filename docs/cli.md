# Using the agnthub CLI

Build and run the CLI from a clone of this repository (or use a [release](../README.md#install)):

```sh
make build
./bin/agnthub add ./path/to/source -l                   # list the source's agents (--list)
./bin/agnthub add ./path/to/source                      # choose agents and harnesses interactively
./bin/agnthub add ./path/to/source --agent reviewer --harness claude --harness codex
./bin/agnthub add owner/repo --agent '*' --harness claude --yes
./bin/agnthub add owner/repo --agent reviewer --harness all --yes
./bin/agnthub add owner/repo --all --global --extra omp.profile=work
./bin/agnthub ls                                        # list (alias ls), -H claude to filter
./bin/agnthub check                                     # source changes and local drift, no writes
./bin/agnthub update reviewer                           # preview, approve, apply newer content (alias upgrade)
./bin/agnthub restore --yes --extra omp.profile=work    # recreate exactly what the lock records
./bin/agnthub rm                                        # choose installed agents to remove (alias rm)
./bin/agnthub remove reviewer --harness omp --extra omp.profile=work
./bin/agnthub remove --clean-dependencies
```

## Commands and flags

The command surface follows [skills.sh](https://skills.sh) (`npx skills`) where the agnthub contract allows, so the same habits work for agents:

| Command | Alias | What it does |
| --- | --- | --- |
| `add <source>` | `a` | Preview and install agents from a repository, Git URL or local directory |
| `list` | `ls` | List the agents agnthub installed (`-g` global, `-H <harness>` filter, `--json`) |
| `remove [agent...]` | `rm` | Remove installed agents; without names a terminal user picks them from a list |
| `check [agent...]` | | Show available updates and local drift without writing |
| `update [agent...]` | `upgrade` | Preview and apply newer content |
| `restore` | | Recreate exactly what `agnthub-lock.json` records |
| `auth login` / `auth status` / `auth logout` | | Save, inspect or remove the agnthub.sh API key that raises the registry API's rate limits (see [API key and rate limits](#api-key-and-rate-limits)) |
| `mcp install` / `mcp uninstall` | | Add agnthub's hosted MCP server to your harnesses, or remove it (see [AI agents (MCP)](#ai-agents-mcp)) |
| `completion <shell>` | | Print a bash, zsh, fish or PowerShell completion script |

Shared flags: `-g/--global` (user scope instead of the project), `-y/--yes` (no prompts), `--json` (machine-readable output, never prompts), `-a/--agent` (agent definitions), `-H/--harness` (harnesses; skills.sh target names such as `claude-code`, `github-copilot` and `gemini-cli` are accepted), `--extra <harness>.<key>=<value>`, `add -l/--list` and `add --all`. `--agent '*'` selects every agent of the source and `--harness all` (or `--harness '*'`) every supported harness; either cannot be combined with other values of the same flag. `--agent` has no `all` alias because an agent can be named `all`. `--all` is shorthand for `--agent '*' --harness all --yes`. `--allow-without-shell` (`add`, `update`, `restore` and `check`) installs agents that would lose the shell access they use where a harness cannot grant it (see Reduced capability under [Behavior](#behavior)). `agnthub --help` and `agnthub <command> --help` show grouped commands, flags and examples; `agnthub --version` (or `-v`) prints the version.

Output: in a terminal, plans, tables, errors and help are styled (lipgloss/fang) and slow steps (fetching sources, resolving dependencies, running the skill installer) show a transient spinner on stderr. Redirected output, `NO_COLOR` and `TERM=dumb` give plain text without colors or spinners, errors become a single `error: ...` line on stderr, and `--json` prints only JSON on stdout.

Plans (`add`, `update`, `restore`, `remove`), their results, `check` and `list` print as tables. A plan starts with a status line (emoji, status, the source in bold with its `@commit` dimmed, and the scope as a cyan tag), followed by the harnesses with their settings such as the omp profile (settings and undetected harnesses dimmed). Then come one `AGENT  HARNESS  ACTION  PATH` row per file that changes (agents in bold, `+ create` green, `~ update` yellow, `- delete` red, the directory of each path dimmed), sorted by agent then harness, a bold yellow `! reduced: <agent> on <harness> goes without <capabilities>` line for each listed row that installs with reduced capability (a line of its own, never folded into the notes), the notes under the table, refusals in a red section of their own (`AGENT  HARNESS  REASON`), and a totals line such as `12 to create · 0 to update · 0 to delete` with only non-zero counts colored. Everything under the status line shares one indent, the measured width of the status emoji and its space, so it lines up with the status text, and these blocks are separated by exactly one blank line (also before the prompt). Agent × harness pairs that need no action are not listed; a sentence under the table counts them (`16 agents were already correct in their harnesses, so no action was needed.`, dimmed). Reused skills are counted the same way under the skills table, and `check` lists only artifacts with an update or local drift. Paths are relative to the project inside it, `~/...` under your home directory and absolute elsewhere. A note shared by several agents (for example `converted from the claude variant`) prints once with the listed rows it applies to; a note about a single agent marks its rows with `[1]`, `[2]`... and is listed under the table; a note about a whole harness (omp's project directory shared by every profile) prints once in the header; notes of unlisted rows are dropped. When `add`, `update` or `restore` has nothing to do (no file to create or update, no skill to install, no receipt to record), there is no prompt: it prints `✅ Up to date`, the harnesses and the sentence in green, writes nothing and exits 0, with or without `--yes` and in or out of a terminal (`--json` is unchanged). After you approve a plan shown in the terminal, the result is only the status line (`✅ Installed · source@commit · scope`) and the totals, plus anything new such as skill installer runs or failures; without a preview (`--yes`, or no terminal to prompt in) the result prints the table once. Choosing Cancel prints a dimmed `Cancelled; nothing was written.` on stderr and exits 1. Emoji mark the status line (📋 plan, ✅ done or up to date, ❌ refused or failed) and the refusal section, never an aligned column. Plain output (redirected, `NO_COLOR`, `TERM=dumb`) has no escape sequences and no emoji, without ASCII stand-ins, and therefore no indent under the status line; the `+`, `~` and `-` action symbols stay. Tables fit the terminal width (or `COLUMNS`): paths are shortened in the middle with `…`, reasons wrap, and when even that does not fit each row stacks onto its own lines. Redirected output without `COLUMNS` is never shortened.

Intentional differences from skills.sh:

- skills.sh's `--agent` names the coding tool to install into; agnthub installs *agents* into *harnesses*, so `-a/--agent` selects agent definitions (skills.sh's `--skill`) and `-H/--harness` the coding tools (skills.sh's `--agent`). `skills add owner/repo -s pr-review -a claude-code` becomes `agnthub add owner/repo -a reviewer -H claude`.
- Several values are given by repeating the flag (`-H claude -H codex`); skills.sh's space-separated lists (`--agent claude-code cursor`) are not accepted because an agnthub source argument could be mistaken for one.
- `--yes` never selects everything implicitly: with more than one agent it needs `--agent` (or `'*'`), and with no `--harness` it fails instead of guessing harnesses. Running inside an agent does not switch agnthub to non-interactive mode; only `--yes`, `--all`, `--json` or a non-terminal stdin/stdout do.
- `--yes`, `--all` and `--json` never reduce a plan: a blocked item fails the whole run before anything is written. skills.sh has no equivalent preview or refusal.
- agnthub writes agent files directly (no `--copy`/symlink choice) and records ownership, so `remove` deletes only unchanged files it installed; `remove --all` is not offered.
- `--extra <harness>.<key>=<value>` (e.g. `omp.profile=work`) has no skills.sh counterpart. `check` and `restore` (skills.sh's `experimental_install`) are first-class; skills.sh's `use`, `init`, `find` and `experimental_sync` have no agnthub command yet (search agents on [agnthub.sh](https://agnthub.sh)).

See the [skills.sh reference](research/skills-reference.md) for the full skills.sh command surface this was compared against.

## Behavior

Sources are explicit local directories (`./dir`), GitHub repositories (`owner/repo[#ref]`) or Git URLs. Harness settings use repeatable `--extra <harness>.<key>=<value>` (for example `--extra omp.profile=work`). The project lock is `agnthub-lock.json`; user-local ownership records live under `$XDG_STATE_HOME/agnthub/`.

Without `agnthub.yaml`, a source's agents are its portable definitions (root `AGENT.md`, `agents/<id>.md`, `agents/<id>/AGENT.md`), the files in each harness's native agent directory, and the agents of the Claude Code plugins it packages: every `.claude-plugin/marketplace.json` entry whose `source` is a directory inside the repository, and the repository itself when it has a root `.claude-plugin/plugin.json`. A plugin's agents are the files its `agents` field lists (paths starting with `./`, inside the plugin) or, without that field, every `.md` file under its `agents/` directory; they are Claude Code Variants, and `--list` names the plugin each comes from. Plugin sources in other repositories (`github`, `url`, `git-subdir`, `npm`, `archive`, `command`) are listed as problems and never fetched. Claude Code ignores `permissionMode`, `hooks`, `mcpServers` and `initialPrompt` in plugin agents, so agnthub installs a plugin agent without them and the plan notes each omission; an agent whose instructions use `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` or `${user_config.…}` needs its plugin and is refused, with the Claude Code command that installs the plugin itself in the reason (`/plugin install <plugin>@<marketplace>`, or `/plugin install <plugin>` for a root plugin). Two different definitions of one agent are ambiguous and refused until `agnthub.yaml` chooses; identical copies (one agent shipped in several plugins) are one agent. See [ADR 0011](adr/0011-claude-code-plugin-layouts.md) and [Claude Code plugins](research/claude-code-plugins.md).

In a terminal, `add` asks which agents and which harnesses to install into: every supported harness (Claude Code, OpenCode, Codex, GitHub Copilot CLI, Cursor, Gemini CLI, omp) is offered and the ones detected locally are preselected. It then previews the plan (a row per agent and harness with its destination, plus dependencies, scope, effective harness settings such as the omp profile, and notes; see Output above) and writes only after you approve. If some items are blocked (a conflict with an unmanaged or locally edited file, an incompatible conversion, an agent that would lose its shell without `--allow-without-shell`, or a destination unavailable in the chosen scope), you may explicitly approve applying only the valid items; the refused ones are listed with their reason. `--json` still reports each item's Variant (`native` or `generated`) and absolute path. Set `ACCESSIBLE=1` (or `TERM=dumb`) for numbered line prompts instead of the terminal UI; redirected output is plain text.

Scope is the project in the current directory unless `--global` is given. The one exception is your home directory (or any directory above it), which is no project: harnesses would apply project files there to projects below it or read them as user configuration (`~/.omp/agents` beside omp's user directory `~/.omp/agent/agents`, `~/.opencode/agents`, `~/.github/agents`; `~/.claude/agents` *is* Claude Code's user directory). Run there, `add` installs into user scope as `--global` does and prints a `note:` line on stderr saying so; `--global=false` (or `scope: project` over MCP) is refused instead. `list`, `check`, `update`, `restore` and `remove` run there use user scope too. A project lock agnthub 0.4.7 and earlier left in the home directory (`~/agnthub-lock.json`) is the exception: while it records installations, those commands use it with a `note:`, so `agnthub remove <name>` run in the home directory removes such an install and deletes the lock once it is empty; `update` and `restore` refuse to rewrite it. User-scope installs also refuse a relative `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME` or `GEMINI_CLI_HOME`, which those harnesses resolve against the directory they run in. Where each harness loads agents from is in [Agent directories and project discovery](research/harness-agent-formats.md#agent-directories-and-project-discovery-runtime-verified-2026-11-04).

`--yes`, `--all` and `--json` never prompt and never reduce a plan: any blocked item fails the whole run before anything is written. `--yes` needs an explicit `--agent` when the source has more than one agent. `--all` selects every agent and every supported harness and cannot be combined with `--agent`/`--harness`; `--all --extra omp.profile=work` applies the profile to omp only. `--json` prints only the machine-readable plan (status, scope, harnesses with detection and effective settings, items, summary) and needs `--yes` or `--all` to apply. Each item has its `action`, the `reason` when it is refused, its `notes`, `reduced` (the capabilities the installed agent goes without, e.g. `["web search"]`) and `optIn` (`allow-without-shell` when installing it needs that flag; such an item is `incompatible` until the flag is given).

Git sources (`owner/repo#v1.2.0`, `https://host/team/agents.git#main`, `git@host:team/agents.git#<full-commit-sha>`) are fetched with the system `git` using your existing credentials (credential helpers, SSH agent); agnthub never stores or prints them. The ref (branch, tag, full commit SHA, or the default branch when omitted) is resolved once to a commit, which the lock records. A source fetched over SSH (`git@host:path` or `ssh://...`, including dependency sources) is locked with `"transport": "ssh"` and its credential-free clone URL, so `check`, `update` and `restore` refetch it over SSH; sources without a recorded transport (https, and locks written before transports were recorded) are refetched over https. Content is read straight from Git objects without a checkout, so repository filters, hooks and LFS never run; symlinks and submodules are skipped. Installing from a source never contacts the agnthub registry.

Agent Dependencies declared in `agnthub.yaml` (common, plus additions on a Harness Variant) install with the selection: the plan shows each companion with origin `dependency`, its pinned source and revision, and the agent that required it. Same-repository references use the selected snapshot; external references name a Git source (`owner/repo#ref` or a Git URL; never a local path), and each source/ref is fetched once. Companions use the same Harnesses, scope and Harness settings (such as `omp.profile`) as the direct selection and are locked under their own source. Cycles, missing or ambiguous agents, one agent required at two revisions, and incompatible companions refuse the plan before anything is written. A dependency is a presence requirement, not a promise of runtime delegation.

Skill Dependencies (`dependencies.skills: [{source, skill, minVersion?, maxVersion?}]`) are preflighted per Harness before anything runs. agnthub looks for a visible copy in that Harness's effective precedence order (in the same scope and Harness settings, e.g. the omp profile) and reuses a compatible one without taking ownership; bounds are inclusive and need a strict semantic `metadata.version` in the skill's own `SKILL.md` (missing or non-semver versions never satisfy a bound; prereleases need a prerelease bound). A higher-priority incompatible copy shadowing a compatible one, incompatible existing content, a skill the Harness configuration disables, or a requested source revision that does not satisfy the bounds refuses the plan. Missing skills install through the skill installer, pinned to the validated commit, and are then verified on disk (identity, exact source content, version, scope, and that the Harness would load that copy) before any dependent agent file is written. If the installer fails or verification fails, no agent file is written and the changes observed in skill locations are reported; agnthub does not roll back the installer or delete pre-existing skills. The lock records each verified skill (source, revision, version, digest, `installed` or `reused`); agnthub only owns skills its own installer run created.

The skill installer is [skills.sh](https://skills.sh) by default. Replace it in `~/.config/agnthub/config.yaml` (`$XDG_CONFIG_HOME/agnthub/config.yaml`); sources can never supply commands:

```yaml
skillInstaller:
  executable: npx            # a command in PATH or an absolute path; run without a shell
  args: [--yes, skills, add, "{source}", --skill, "{skill}", --agent, "{target}", --yes]
  projectArgs: []
  globalArgs: [--global]
```

`{source}` is the source pinned to the validated commit, `{skill}` the skill name and `{target}` the backend target the Harness adapter selects (`claude-code`, `codex`, `opencode`, `github-copilot`, `cursor`, `gemini-cli`; omp uses skills.sh's shared `universal` target, which writes `.agents/skills`). Each template stays one argument; unknown placeholders or invalid configuration fail before anything runs. When you opt out of sharing (below), the skill installer runs with `DO_NOT_TRACK=1` and `DISABLE_TELEMETRY=1`. See [skill dependency research](research/skill-dependencies.md) for each Harness's discovery locations and precedence.

Install reports: after an `add` or `update` that created or replaced files from a GitHub repository that an anonymous check shows is public, the CLI tells the registry (`https://api.agnthub.sh`; override with `AGNTHUB_API_URL` or `apiURL:` in `~/.config/agnthub/config.yaml`) the owner/repo, the installed commit and, per agent, its id, whether it was installed directly or as a dependency, the harness ids it placed and a random identity kept for that repository and agent in `$XDG_STATE_HOME/agnthub/identities.json`. The registry counts these reports only for agents of repositories it already lists; a report never adds a repository to the registry (repositories are submitted on the web app by a GitHub-signed-in user) and reports for unlisted repositories are ignored and not stored. Nothing else is sent: no paths, profiles or other harness settings, local, private or non-GitHub sources, or parent agents. With an [API key](#api-key-and-rate-limits) configured, the report carries it in its `Authorization` header for the signed-in install limit; without one it is anonymous. Reporting is best-effort (at most a few seconds) and never changes the command's result: a rate-limited report is dropped, never retried, and an unusable key sends nothing. `restore` and no-op reinstalls report nothing. Set `DO_NOT_TRACK` or `DISABLE_TELEMETRY` to any non-empty value to send nothing at all.

Codex agents install as standalone TOML under `.codex/agents/` (project) or `$CODEX_HOME/agents/` (global, default `~/.codex/agents/`). Authored Codex Variants install byte-for-byte after schema validation; conversion writes `name`/`description`/`developer_instructions`, plus `features.shell_tool = false` when the agent withholds the shell. Codex has no per-agent tool allowlist or read-only mode, so an agent that withholds edits is incompatible with Codex. Codex runs custom agents in the parent session's sandbox: an authored Variant declaring `sandbox_mode = "read-only"` is refused on Codex, where the agent could still edit files, and converts to the other harnesses without edit tools (on Cursor that means `readonly`, which also takes the shell, so it needs `--allow-without-shell`); `workspace-write` and `danger-full-access` install on Codex with a note that the session's sandbox applies, and are omitted elsewhere with a note. `features.multi_agent = false` installs on Codex with a warning that Codex does not enforce it in an agent file, and converts to the other harnesses without delegation. Variants that try to set other parent-owned configuration (approvals, `sandbox_workspace_write`, permissions, provider, MCP servers, profiles, hooks) are refused, and `config.toml` is never modified.

Agents published only as one harness's native file (for example `.claude/agents/*.md`) install on the other harnesses by conversion: without an authored Variant for the target, agnthub converts the portable core, else another authored Variant (Claude Code first); when several convert, the first that converts exactly under the rules before ADR 0012 wins, then the first that needs one of ADR 0012's readings (a portable core with Claude Code fields, a field its own harness ignores, a lowered behavior, agent-scoped MCP servers), then the first with reduced capability, then the first that loses the shell, so an install never changes source because another of the agent's files became convertible. Portable definitions (root `AGENT.md`, `agents/<id>.md`, `agents/<id>/AGENT.md`) are read as Claude Code agents: their frontmatter has its Claude Code meaning, with the same notes and refusals as a `.claude/agents/` file, plus refusals for the delegation lists of other harnesses' dialects (`agents`, `spawns`, `subagents`, `handoffs`) and for instructions that use `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` or `${user_config.…}`, which only resolve inside an installed plugin. Name, description and instructions always carry; a whole-tool rule such as `WebFetch(*)` or `Bash(*)` is the plain tool, as Claude Code reads it; tool allowlists translate by capability (read, search, edit, shell, web fetch/search, delegation) into each harness's own form (OpenCode `permission`, Copilot tool aliases, Gemini and omp tool names, Cursor `readonly`); model strings are carried only from a portable core to Claude Code (which also keeps its `permissionMode` and `Bash(...)` rules), elsewhere the converted agent uses the harness default model and the plan says so; cosmetic fields such as `color` are omitted with a note. Allowlisted names with no equivalent (lowercase `read`, `All`, `ListMcpResourcesTool`, a bare MCP server name such as `playwright`) are left out with a note, which only withholds them; Claude Code itself grants nothing for names it does not know. On Cursor, which reads one line per key and keeps the value as written, the description is written on one line, quoted when it must be; an authored Cursor agent whose description spans several lines installs with only that line rewritten. A target that cannot enforce what the agent declares (MCP tools it cannot address, real hooks, the `dontAsk` permission mode, approval prompts for anything but the shell, agent-scoped MCP servers outside Gemini CLI, or an exclusion it cannot withhold) is reported incompatible with the reason. A permission mode that only approves more without asking (`acceptEdits`, `auto`, `bypassPermissions`) is dropped with a note: the other harness asks for approval as usual, which is at least as strict. `permissionMode: plan` converts as a read-only tool policy, without edits, shell, delegation or MCP tools (each one the agent used is shown as reduced): Claude Code keeps the mode, Codex refuses it (it cannot withhold edits), and an agent whose tools include the shell loses it, which needs `--allow-without-shell`. Background agents (`background: true`, Cursor `is_background`) run in the background only on Claude Code and Cursor; elsewhere they install to run in the foreground, with a note. Persistent memory (`memory`) and preloaded skills (`skills`) only add to what an agent knows, so they never make a target incompatible. A turn limit (`maxTurns`) maps to OpenCode `steps` and Gemini CLI `max_turns`; on the other harnesses the agent installs with a short instruction to finish within about that many turns, and the plan notes the limit isn't enforced. Claude Code frontmatter keys Claude Code itself ignores are omitted with a note, unless they read as a tool or permission restriction (`readonly`, `permissions`, `allowed-paths`…), which still refuses. `allowed-tools`, a skill field Claude Code ignores in agents, is the exception: other harnesses enforce it as the tool allowlist (what both `tools` and `allowed-tools` allow, when both are set), and an authored Claude Code agent with it installs on Claude Code as written with a warning that Claude Code does not enforce it. The same holds for the restriction-like fields other harnesses ignore in their own agents: Cursor `tools` (read as a Claude Code allowlist), Copilot CLI `allowed-tools` (a second allowlist), `agents` (delegation limited to those agents) and `maxTurns`, and Codex `features.multi_agent = false` install on their own harness with that warning and are honored elsewhere where the target can express them. A field set to what omitting it does is omitted with a note rather than refused: `permissionMode: default` (or `manual`); `hooks` whose every event is one Claude Code does not run (event names are case-sensitive, so the `pre`/`post` scripts of a widely copied template are ignored); and `hooks`, `mcpServers`, `isolation`, `initialPrompt`, `maxTurns` or an ignored restriction-like key left empty (`[]`, `{}`, blank, `false`). An empty allowlist (`tools: []`, `allowed-tools: []`) allows nothing and `hooks: []` keeps Claude Code from loading the agent, so neither counts as empty. Authored Copilot CLI and Cursor agents may carry documentation keys those harnesses ignore (`color`, `title`, `category`…); they install as written with a note. Codex `nickname_candidates` installs on Codex and is omitted elsewhere.

Isolation and manual-only invocation are carried where a harness has them and emulated elsewhere ([ADR 0014](adr/0014-emulate-worktree-isolation-and-manual-only-invocation.md)). `isolation: worktree` is native on Claude Code; elsewhere an agent that can run any shell command installs with an instruction, at the top of its instructions, to create a git worktree, work and commit only there and report its path and branch, shown as `! reduced: … goes without isolation` (`reduced: ["isolation"]` in `--json`); an agent that edits without such a shell is refused there, since it cannot create a worktree, and one that neither edits nor runs commands installs unchanged. A Copilot CLI agent with `disable-model-invocation: true` (or `infer: false`) keeps the field on Copilot CLI and becomes a primary agent (`mode: primary`) on OpenCode, which the model never delegates to; elsewhere its tools are unchanged and its description starts with "Use only when the user explicitly asks for this agent.", shown as `! reduced: … goes without manual-only invocation`.

- **Preloaded skills** become Copilot CLI's `skills` or omp's `autoload-skills`. On the other harnesses, a short section appended to the instructions tells the agent which skills to load; OpenCode and Gemini CLI allowlists also gain their skill tool. agnthub never installs those skills.
- **Memory** is emulated the same way, with a section naming the agent's notes folder and its `MEMORY.md` index. Project and local scope use Claude Code's folders `.claude/agent-memory/<name>/` and `.claude/agent-memory-local/<name>/`. User scope uses `~/.claude/agent-memory/<name>/` on OpenCode and omp, and `~/.cursor/agent-memory/<name>/` on Cursor. Elsewhere, and for agents that cannot edit files, the plan notes that the agent starts each session without its notes.

Agent-scoped MCP servers (Claude Code `mcpServers` and Copilot CLI `mcp-servers` with inline configurations) convert only to Gemini CLI, as the agent's own `mcp_servers` (a note says the server runs when the agent is used); every other conversion target refuses such an agent (Claude Code too, for a portable core), while an authored Claude Code or Copilot CLI agent still installs on its own harness as written. A server referenced only by name (configured elsewhere), a setting Gemini CLI has no equivalent for, or a value using `${{ secrets.… }}` or `${VAR:-default}` substitution refuses Gemini CLI too.

Shell rules limited to some commands carry exactly from Claude Code `Bash(<pattern>)` entries (the legacy `Bash(git log:*)` reads as `git log *`) to OpenCode `permission.bash` patterns, written in order after `'*': deny`, since OpenCode applies the last matching rule; an OpenCode agent's own `permission.bash` patterns install on OpenCode as written. Every other harness, and Claude Code for an OpenCode source, cannot limit the shell to commands, so there the agent goes without the shell (see below); so does an OpenCode agent whose shell asks for approval (`bash: ask`).

Reduced capability: when a target cannot grant a capability the agent uses and the only faithful choice is to withhold it, the agent installs without it, never with more access than it declares, and the plan prints a `! reduced:` line for it (`reduced` in `--json`). That covers web search on Copilot CLI (Copilot CLI offers custom agents no web search tool; web fetch, when allowed, stays as `web`), delegation on Gemini CLI (subagents cannot invoke agents), the MCP tools of an agent that becomes read-only on Cursor (`readonly` blocks every MCP tool call), and delegation limited to some agents (Copilot CLI `agents`, omp `spawns`): omp keeps the limit as `spawns`, Claude Code, OpenCode, Copilot CLI and Gemini CLI withhold delegation, and Cursor and Codex, which can neither limit nor withhold delegation, install it with a note, as for any agent that withholds delegation there. Losing the shell needs the explicit `--allow-without-shell` (MCP `allow_without_shell`): an agent that uses the shell but no edits on Cursor (whose only restriction, `readonly`, blocks every shell command; an agent that edits but withholds the shell stays refused there), a shell limited to some commands outside OpenCode, and `permissionMode: plan` with a shell. Without the flag such an item is refused with `run again with --allow-without-shell to install it without shell`, and `--json` marks it `optIn: allow-without-shell`. The opt-in is per command and not recorded in the lock: `update` and `restore` of such an agent need the flag again, and `check` takes it to compare against what `update --allow-without-shell` would install.

See [ADR 0009](adr/0009-cross-harness-conversion-through-shared-semantics.md) and [ADR 0012](adr/0012-portable-cores-as-claude-and-reduced-capability.md).

`remove <agent>...` deletes only the selected agents' files that agnthub can prove it installed (an ownership record or the lock's digest) and that are unchanged since; a modified or replaced file is refused and left in place, unrelated native configuration is never touched, and the lock and ownership records are updated to match what actually happened (a failed deletion keeps its state and fails the run). `--harness` limits the harnesses and `--extra` selects the recorded binding: a file several bindings share (one project `.omp/agents` file installed for omp profiles `hep` and `work`) keeps the file and drops only the selected binding until its last binding goes. Several recorded bindings without `--extra` are asked about in a terminal and refused otherwise. An agent another remaining agent requires is refused. `--yes`/`--json` follow `add`: unattended runs apply only when every selected artifact can be removed.

Removing an agent never removes its companion agents or skills. `remove --clean-dependencies [name...]` is the separate, explicit cleanup: it removes a companion agent or a skill only when agnthub installed it (origin `dependency`, or a skill directory agnthub's skill installer created), it is unchanged, and no remaining agent in the same harness binding requires it. A skill directory also stays while another binding, another project's installation or another visible lock (the global lock, locks of projects this machine installed into) uses it. Reused skills (compatible copies that were already present) are never deleted: once no agent requires them they only leave the lock. Locks written before requirements were recorded cannot prove a dependency unused, so cleanup preserves it. Preserved items are reported with their reason. The skill installer's own files (for example skills.sh's `skills-lock.json`) are left alone.

`check [agent...]` resolves each locked agent's recorded ref (or default branch) to its current commit and compares, per Harness, what agnthub would install now with the lock: each agent is up to date, has an update available (content, Variant or converter change), is a new or no-longer-required dependency, or is unavailable (unreachable source or ref, or an agent the source no longer provides). Local drift (modified or missing files) and the recorded Harness bindings (such as the omp profile) are shown; `--json` prints the same report. Nothing is written.

`update [agent...]` (default: every direct agent) resolves the same newer content with its current dependency closure, previews content, Variant, dependency and skill changes plus the plan, and writes only after approval (`--yes` noninteractively). Locally modified or unmanaged files are never overwritten: the plan is refused (or, in a terminal, you may explicitly apply only the valid items). Dependencies the new revision no longer requires stay installed. Every artifact keeps the binding it was recorded with: an omp agent installed while profile `hep` was active is updated in `hep` even when another profile is active now, `--extra` naming a different binding is refused instead of retargeting, and a shared file with several recorded bindings needs `--extra` or a terminal choice.

`restore` recreates the installation the lock records, e.g. in a fresh clone: each agent is fetched at its locked commit, its source bytes must match the locked `sourceDigest`, it is regenerated with the recorded converter (an unsupported converter id/version is refused) and every artifact must equal its locked digest before anything is written; skills are installed through the skill installer pinned to their locked commit and verified against the locked digest. An unavailable commit, changed bytes or a mismatch is an error, never a reason to substitute newer content (`update` is the explicit way forward). Recorded bindings are reused; on a machine without them, Harnesses with settings need an explicit binding (`--extra omp.profile=work`, or a terminal choice). Restore never moves or deletes another profile's installation, never replaces a locally modified file and never replaces a shared file on behalf of a different binding. The lock never contains user-local state: absolute project paths, Harness settings and installation times stay in the ownership records.

## API key and rate limits

Everything works without an account. The registry API limits anonymous callers per network address; with an agnthub.sh API key, the limits are higher and charged to your account, so several machines or a shared network address no longer share one allowance:

| Tier | Anonymous (per address) | With an API key (per account) |
| --- | --- | --- |
| `search` (search, listings, categories) | 60/min, burst 30, and 2,000/hour | 600/min, burst 120 |
| `detail` (repository and agent pages, `/v1/me`) | 300/min, burst 100 | 3,000/min, burst 500 |
| `install` (install reports) | 30/min | 120/min |

```sh
agnthub auth login                         # opens https://app.agnthub.sh/api-key, then asks for the key (hidden)
agnthub auth login --no-browser            # print the page URL only
pbpaste | agnthub auth login --with-key-stdin
agnthub auth status                        # key source, agh_…last4, GitHub account, current limit
agnthub auth status --json
agnthub auth logout                        # remove the saved key
```

- **Getting a key:** on [app.agnthub.sh/api-key](https://app.agnthub.sh/api-key) (also *API key* in the account menu), sign in with GitHub and create a key. The site shows it once, right after you create or rotate it, and afterwards only as `agh_…7f3a`. Rotate or revoke it there.
- **`auth login`** opens that page in the browser (in a terminal, unless `--no-browser`; the URL is always printed), reads the key at a hidden prompt (or from standard input with `--with-key-stdin`), checks it with `GET /v1/me` and saves it as `apiKey:` in `~/.config/agnthub/config.yaml` (`$XDG_CONFIG_HOME/agnthub/config.yaml`), rewritten atomically with mode `0600` and the rest of the file kept. It prints `Signed in as <github login>`. Without a terminal it needs `--with-key-stdin`.
- **`AGNTHUB_API_KEY`** wins over the saved key, for CI and scripts. `auth logout` removes only the saved key; it cannot unset the variable and says so while it is set.
- **Where it goes:** the CLI and install reports send `Authorization: Bearer <key>` only to the configured registry API origin (`AGNTHUB_API_URL`, `apiURL:` or `https://api.agnthub.sh`; scheme, host and port must match), never to GitHub or any other host, and never in a redirect to another host. A key that does not start with `agh_` is refused locally before any request; it never falls back to anonymous requests.
- **Scope:** a key reads the registry and reports installs. Every other operation (stars, submissions, administration) answers 403 to a key.
- **Rejected key:** a revoked, rotated or malformed key gets `401` from the API, and the command fails with `Your agnthub API key was rejected (revoked or rotated?). Run agnthub auth login or unset AGNTHUB_API_KEY.` It is never retried anonymously.
- **Rate limited:** on a `429`, a `Retry-After` of 10 seconds or less is waited out once and the request retried; a longer one fails with `agnthub.sh rate limit reached; try again in N s`, plus `(sign in with agnthub auth login for higher limits)` when no key was sent. Install reports are never retried or waited for.
- **Headers:** every rate-limited API response carries `RateLimit-Policy: "<tier>";q=<limit>;w=<window seconds>` and `RateLimit: "<tier>";r=<remaining>;t=<seconds to reset>` (IETF draft), plus `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (Unix seconds) and `X-RateLimit-Resource`; a `429` also carries `Retry-After`. `auth status` shows the limit from these headers.

## AI agents (MCP)

AI agents use agnthub through the hosted MCP server at [`https://mcp.agnthub.sh`](https://app.agnthub.sh/mcp) (sign-in with GitHub, or an API key). Its `install_agents` tool checks agents against the registry and returns the exact `npx -y agnthub-cli@latest add … --yes` command, which the agent runs with its shell tool after the user confirms, so installs keep every protection of `agnthub add`. The CLI itself has no MCP server: the local stdio server (`agnthub mcp`) was removed in v0.5.0. `agnthub mcp install` and `agnthub mcp uninstall` set the hosted server up in your harnesses, or remove it; manual setup for every harness is at [app.agnthub.sh/mcp](https://app.agnthub.sh/mcp).

```sh
agnthub mcp install                                   # pick harnesses and omp profiles from a list
agnthub mcp install --harness claude,codex --yes      # (or -H claude -H codex)
agnthub mcp install --harness all --yes --json        # every detected harness
agnthub mcp install --harness omp --profile default --profile work --yes
agnthub mcp install --harness cursor --scope project --yes
agnthub mcp install --harness claude --api-key --yes # a bearer header instead of signing in
agnthub mcp uninstall                                 # pick from the installs found
agnthub mcp uninstall --yes                           # remove every one found
```

### `mcp install`

1. **Detect.** install looks at the harnesses detected on this machine (the same detection as `add`: the harness's command on `PATH` or its configuration directory, honoring `CLAUDE_CONFIG_DIR`, `OPENCODE_CONFIG_DIR`/`XDG_CONFIG_HOME`, `CODEX_HOME`, `COPILOT_HOME`, `GEMINI_CLI_HOME` and omp's `PI_CONFIG_DIR`/`PI_CODING_AGENT_DIR`) and, for omp, at every profile: the default one and each directory under `~/.omp/profiles/`. For each it reads the configuration and finds what the `agnthub` entry is now: none; the hosted server (**already installed**); an older agnthub setup (the former `https://api.agnthub.sh/mcp` or `https://mcp.agnthub.sh/mcp` URL, the local server `npx … agnthub-cli mcp` or `agnthub mcp`, or the hosted URL in a shape the harness does not read as such); or an `agnthub` entry agnthub did not write (another URL or command).
2. **Choose.** In a terminal, a list of the detected harnesses and omp profiles (space toggles, ctrl+a toggles all, enter confirms): the ones without agnthub are preselected, installed ones are marked `already installed`, older setups `select to update` and foreign entries `select to replace` (replacing asks once more). Undetected harnesses are named on one dimmed line. Without a terminal, or with `--yes` or `--json`, choose with `--harness` (comma-separated or repeated; `all` for every detected harness; a named harness is set up even when it is not detected) and `--profile <omp profile>` (repeatable, `default` for the default profile; implies `--harness omp`; a named profile must exist, agnthub never creates one). Without `--harness` and a terminal, install fails and writes nothing.
3. **Configure.** Each selected harness gets an `agnthub` server, Streamable HTTP, at `https://mcp.agnthub.sh`, in its user configuration, or with `--scope project` in the current project's (refused in the home directory, which is no project, as with `add`). Older agnthub entries are replaced; a foreign `agnthub` entry is skipped unless you confirmed it in the list or passed `--force`.
4. **Sign in.** No secret is written: each harness signs in with GitHub through the MCP authorization flow (OAuth), and install prints the exact step for each harness it configured. `--api-key` writes your agnthub API key (`AGNTHUB_API_KEY`, else the key `agnthub auth login` saved: the one `agnthub auth status` shows) as an `Authorization: Bearer` header instead, so no sign-in is needed. It warns on stderr that the key is then stored in plain text in each harness's configuration file, and again for a file other users can read; files agnthub creates are mode 0600. Every supported harness accepts that header. `--api-key` is refused with `--scope project`, whose files are often committed.

| Harness | How | User configuration | `--scope project` | Sign in afterwards |
| --- | --- | --- | --- | --- |
| Claude Code | `claude mcp add --transport http --scope user agnthub https://mcp.agnthub.sh` (`claude mcp remove` first to replace an older entry) | `~/.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json`) | `claude mcp add --scope project` → `.mcp.json` | `claude mcp login agnthub`, or `/mcp` → agnthub → Authenticate |
| OpenCode | file edit (`opencode mcp` has no remove) | `~/.config/opencode/opencode.json` or `.jsonc` (`$OPENCODE_CONFIG_DIR`, `$XDG_CONFIG_HOME/opencode`): `mcp.servers.agnthub` for OpenCode 2, `mcp.agnthub` for OpenCode 1, an unknown version, or a file that already uses that shape (OpenCode 2 reads it too) | `opencode.json` / `opencode.jsonc` | `opencode mcp auth agnthub`, or `/mcps` → agnthub → sign in |
| Codex | file edit (`codex mcp add` drops other entries' comments) | `~/.codex/config.toml` (`$CODEX_HOME`), `[mcp_servers.agnthub]` | `.codex/config.toml` | `codex mcp login agnthub` |
| Copilot CLI | `copilot mcp add --transport http agnthub https://mcp.agnthub.sh` (`copilot mcp remove` first) | `~/.copilot/mcp-config.json` (`$COPILOT_HOME`) | file edit: `.github/mcp.json` | `/mcp auth agnthub` in Copilot CLI |
| Cursor | file edit (no add command) | `~/.cursor/mcp.json` | `.cursor/mcp.json` | `cursor-agent mcp login agnthub`, or `/mcp list` → agnthub → login |
| Gemini CLI | `gemini mcp add --scope user --transport http agnthub https://mcp.agnthub.sh` (`gemini mcp remove --scope user` first) | `~/.gemini/settings.json` (`$GEMINI_CLI_HOME/.gemini`) | file edit: `.gemini/settings.json` (the command refuses untrusted folders) | `/mcp auth agnthub` in Gemini CLI |
| omp | file edit, one per profile | `~/.omp/agent/mcp.json`, `~/.omp/profiles/<name>/agent/mcp.json` | `.omp/mcp.json` (every profile reads it) | `/mcp reauth agnthub` in omp (`omp --profile <name>` for a profile) |

A harness's own command is used only when it is on `PATH`, and never with `--api-key` (the key would show on its command line); otherwise agnthub edits the file.

**Safety of file edits.** The file is parsed first (JSON with comments and trailing commas, TOML for Codex) and a file that does not parse is never changed: that harness fails with the parse error and the others are still done. Only the `agnthub` entry is added, replaced or removed; every other byte, comments and formatting included, stays, new entries follow the file's indentation, and the result is parsed again and compared with the original, so nothing but the `agnthub` entry can differ. The previous file is copied, with its mode, to `~/.local/state/agnthub/mcp-backups/<time>-<harness>[-<profile>]-<file>` (under `$XDG_STATE_HOME` when set), and the new one is written to a temporary file beside it and renamed over it, through symbolic links, keeping the file's mode (0600 for a new file). When a harness's own command is used, its file is backed up the same way and read back afterwards; if the command fails or the file does not then hold the expected entry, the backup is restored.

Output: a status line, then a `HARNESS  PROFILE  ACTION  CONFIG FILE` table (`+ install` green, `~ update` yellow, `= already installed` dimmed, `! skipped` and `! failed` red with the reason under the table), where the backups went, the undetected harnesses, and how to sign in to each harness that was configured:

```text
$ agnthub mcp install --harness all --yes
✅ agnthub MCP server installed · user scope · https://mcp.agnthub.sh

   HARNESS  PROFILE  ACTION               CONFIG FILE
   claude            + install            ~/.claude.json
   codex             ~ update             ~/.codex/config.toml
   omp      default  = already installed  ~/.omp/agent/mcp.json
   omp      work     + install            ~/.omp/profiles/work/agent/mcp.json

   Previous files are backed up in ~/.local/state/agnthub/mcp-backups.
   Not detected: opencode, copilot, cursor, gemini (name one with --harness to set it up anyway).

🔑 Next, sign in with GitHub in each harness
   claude    run `claude mcp login agnthub`, or `/mcp` in Claude Code, select agnthub and authenticate
   codex     run `codex mcp login agnthub`
   omp work  run `/mcp reauth agnthub` in omp (start it with `omp --profile work`)
```

`--json` prints `{"command", "status", "scope", "url", "results": [{"harness", "profile", "scope", "configFile", "before", "action", "mechanism", "command", "backup", "reason", "signIn"}], "notDetected"}`: `status` is `done`, `skipped`, `failed` or `none`; `before` is the entry's state (`absent`, `installed`, `outdated`, `legacy`, `legacy-stdio`, `foreign`); `action` is `install`, `update`, `unchanged`, `skip`, `fail` or `remove`; `mechanism` is `command` or `file`.

Exit status of `mcp install`: `0` when every selected harness is set up (or already was); `1` on an error (invalid flags, a cancelled prompt, no `--harness` without a terminal, or a harness whose configuration could not be changed; the others are still done); `2` when a harness was skipped because its `agnthub` entry was not set up by agnthub (rerun with `--force` to replace it).

### `mcp uninstall`

uninstall reads every supported harness's user configuration (every omp profile included, whether or not the harness is still detected) and, with `--scope project`, also the current project's, and lists only the agnthub entries agnthub set up, in any of the forms above, all selected. With none it prints `No agnthub MCP installs detected.` and exits 0. `--yes` removes every one found without asking; `--harness` and `--profile` narrow the search; without a terminal it needs `--yes` or `--harness`. Removal uses the harness's own `mcp remove` where install uses its `mcp add`, otherwise the same file edit and backup. Other servers, and an `agnthub` entry agnthub did not write, are never removed; a configuration that cannot be read is reported on stderr and left alone. Same table (`- remove` in red) and `--json`. Exit status: `0` when every selected entry was removed or none was found, `1` on an error.

### Bare `agnthub mcp`

MCP client configurations from before v0.5.0 still start `npx agnthub-cli mcp` as a stdio server. Without a terminal on stdin and without a subcommand, `agnthub mcp` (whatever flags such a configuration passes) prints `The local MCP server was removed in v0.5.0. Use the hosted server instead: https://mcp.agnthub.sh (setup: https://app.agnthub.sh/mcp).` and ``Run `npx agnthub-cli mcp install` to configure the hosted server.`` on stderr and exits 1, so the client reports the server as failed; `mcp install` replaces that entry. In a terminal it shows the help of the `mcp` commands.
